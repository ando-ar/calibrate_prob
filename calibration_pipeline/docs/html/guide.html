入力・出力と実行の流れ

学習

学習TOMLの例です。設定値の検証は calibration_pipeline.config.load_config() が行います。

[model]
# 学習SQLが返す元スコアの列名。欠損のない有限値の数値が必要です。
score = "oubo_score"
# 学習SQLが返す確定ラベルの列名。0か1の数値が必要です。
label = "label"
# 推論の出力に付ける予測確率の列名。学習SQLの戻り値には不要です。
probability = "oubo_prob"
# 数値特徴量の列名。NULLとNaNは欠損として扱い、無限値はエラーになります。
# 1,2,3のような数値コードでも、順序に意味があるならこちらへ入れます。
numeric_features = ["seeker_skill"]
# カテゴリ特徴量の列名。順序に意味がない数値コードはこちらへ入れます。
# 文字列・数値いずれの列も受け付け、NULLや学習時に見なかった値も扱えます。
# 数値はパイプラインが決まった規則で文字列に変換してCatBoostに渡します。
categorical_features = ["occupation"]
# 校正評価のECEとプロットを計算するビン数。
bins = 10

SQLは元スコア・特徴量・確定二値ラベルと row_role を返します。

row_role

用途

train

CatBoostの学習

calibrate

後続期間でIsotonic Regressionによる校正

validation

さらに後続期間での評価

SQL作成者が期間の順序・重複・ラベルの確定・母集団・特徴量の取得時点を管理します。 数値特徴量はNULL・NaNを欠損として扱いますが、無限値は使えません。 元スコアは欠損のない有限値、ラベルは数値の0か1、カテゴリ特徴量は文字列または数値の列です。 1,2,3のような数値コードを順序として扱うかカテゴリとして扱うかは、設定のどちらのリストに 列を入れるかで決まります。カテゴリのNULLや学習時に現れなかった値も使用できます。

SQLite用の抽出例です。

-- 合成の紹介履歴を、観測締切の異なる学習・校正・検証期間に分ける。
WITH periods(row_role, start_date, end_date, observed_through) AS (
    VALUES ('train',      '2024-01-01', '2024-02-01', '2024-05-01'),
           ('calibrate',  '2024-05-01', '2024-06-01', '2024-09-01'),
           ('validation', '2024-09-01', '2024-10-01', '2025-01-01')
),
referrals AS (
    SELECT p.row_role, p.observed_through, r.user_id, r.shoukai_dt, r.oubo_score, r.oubo_dt,
           datetime(r.shoukai_dt, '+3 months', 'floor') AS application_deadline
    FROM main.scored_referrals AS r
    JOIN periods AS p
      ON r.shoukai_dt >= p.start_date AND r.shoukai_dt < p.end_date
),
ranked_referrals AS (
    SELECT r.row_role, r.user_id, r.shoukai_dt, r.oubo_score,
           CASE WHEN r.oubo_dt BETWEEN r.shoukai_dt AND r.application_deadline
                THEN 1 ELSE 0 END AS label,
           ROW_NUMBER() OVER (PARTITION BY r.row_role ORDER BY random()) AS sample_rank
    FROM referrals AS r
    WHERE r.application_deadline <= datetime(r.observed_through)
)
SELECT r.row_role, r.oubo_score, f.seeker_skill, f.occupation, r.label
FROM ranked_referrals AS r
LEFT JOIN main.user_feature_daily AS f
  ON f.user_id = r.user_id AND f.snapshot_date = date(r.shoukai_dt)
WHERE r.sample_rank <= 100000
ORDER BY r.row_role, r.sample_rank;

学習・校正の処理は calibration_pipeline.pipeline.fit()、評価は calibration_pipeline.evaluation.metrics() を参照してください。 検証データで校正前後のECE・Brier score・ビンごとの確率と実績率を計算し、JSONとSVGに保存します。

推論

候補はUTF-8 CSVまたはParquetで、1行1候補です。元スコア、user_id、item_id、 特徴量の結合に使う列を含めます。ユーザーIDは10000000〜19999999、求人IDは20000000〜29999999です。 CSVでは8桁の数字、Parquetでは整数型を使います。

入力に candidate_row_id を付け、SQLと同じ接続の一時テーブル calibration_candidates にアップロードします。 推論SQLは各候補に対してちょうど1行、candidate_row_id・元スコア・必要な特徴量を返してください。 推論TOMLは空かコメントのみです。列の設定は学習済みモデルから読み込みます。

-- 推論日の特徴量を結合し、候補行ごとにモデルの入力を返す。
SELECT c.candidate_row_id, c.oubo_score, f.seeker_skill, f.occupation
FROM calibration_candidates AS c
LEFT JOIN main.user_feature_daily AS f
  ON f.user_id = c.user_id AND f.snapshot_date = date(c.shoukai_dt)
ORDER BY c.candidate_row_id DESC;

出力は入力と同じ形式・行順で、確率列を追加します。 入力検証と行の対応は calibration_pipeline.contracts に実装されています。

experimentと再現

--experiments-dir の既定値は experiments/ です。 <model_name>/<trainまたはinference>/<run_id>/ の下に次のファイルを保存します。

保存先

内容

input/

設定・SQL・候補・指定したSQLite DBのコピー

run_metadata.json

開始・終了・状態・入力SHA-256、推論で使った学習run

output/

成功時に公開するモデル・指標・SVG、または推論結果

run IDはJSTの開始時刻で、同秒の実行には連番が付きます。 推論開始時に、成功した学習runのうち開始時刻が最も新しいものを選びます。 --train-run <run_id> で固定できます。モデルは信頼できるexperimentの保存物を使用してください。

--seed の既定値は42です。学習ではCatBoostとSQL、推論ではSQLに使います。 Redshiftの分散実行では、同じseedでも行の割り振りにより抽出結果が変わることがあります。
