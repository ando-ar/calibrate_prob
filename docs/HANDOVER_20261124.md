## 4. Orca オーケストレーション運用手引（引き継ぎの核心）

基本: `orca orchestration worker-start --spec "<自己完結したspec>" --worktree new-child --agent <agent>` → Orca が完了時に coordinator へ通知。**ポーリング禁止**（Orca が起こす）。

- spec には必ず: 作業ディレクトリ/ブランチ戦略（worktree は自動作成されるので、base 指定と HEAD 検証指示）、完了条件、テストコマンド、コミットメッセージ、報告項目を書く。ワーカーは新鮮な文脈から始めるため**自己完結**が必須
- モデル事情: opencode2 は Orca からの起動時モデル指定不可。既定モデルは Orca 管理アカウントの設定で決まる: `C:\Users\aruto\AppData\Roaming\orca\managed-data-accounts\opencode\9f5210c9-7124-4600-a33f-ac4c1b2b5fcf\.config\opencode\opencode.json`（`{"model": "opencode-go/deepseek-v4.1-flash"}` を設定済み。data/opencode/opencode.json も同値）。**deepseek-v4-pro は EU/US 外ホスティングで opencode.ai/console の privacy 設定 Global が必要**（ユーザーは許可済みだが、トークン消費が大きいため注意）
- ワーカーの質問（ask）には `orca orchestration reply --id <msg_id> --body ...` で回答。reply が dispatch_inactive で閉じた場合、ワーカーは既に推奨案で完了していることが多い → 成果物を確認し、ユーザーの決定と異なる部分を coordinator が直す（実績: COMPETITION_DIFFICULTY/SOLUTION_DIVERSITY の §5/§7）
- 長時間バックグラウンド実行でターンを終えるワーカーには `orca orchestration send --to dispatch:<id> --subject ... --body ...` でナッジ（都度継続指示）。ただし「完了通知を待つ」と言われたらナッジをやめて待つ
- ワーカー停止/失敗時: `worker-show` で状態確認 → 必要なら `worker-stop` → `orca orchestration task-update --id <task_id> --status ready --run <run_id>` → `worker-start --task <task_id> --worktree new-child --agent ...` で再開（retry-of は失敗系のみ有効で、停止済みタスクでは task-update 後の --task 起動が実用的）
- 完了済みワーカーの取込み手順（定型）: `git merge <branch>` → `cd synthetic_funnel && uv run pytest -q` → `git push` → `orca orchestration worker-release --dispatch <id>` → `orca worktree rm --worktree "path:<worktree path>" --force --json` → `git branch -D <branch>` → 該当 issue を `gh issue close`。**worktree 削除は orca worktree rm を使う**（git worktree remove より安全。selector は `path:<絶対パス>` が確実）
- ワーカーに人間の承認（websearch 等）が必要な場合、メッセージでは解決不可 → ユーザーに Orca の該当タブで承認するよう案内する
- 単発の小タスクは解放済みワーカーに `send` で再オープンしてもよい（dispatch が閉じると再オープン不可。その場合は新規 worker-start）

## 5. 環境の落とし穴

- Windows で sqlite ファイルはプロセス終了までロックされる → 生成・削除を繰り返す処理は **subprocess 分離**（`seed_batch.generate_seeds` / `build_release.py` が実装済み）
- `synthetic_funnel` と `calibration_pipeline` ともに pytest は dev 依存で `uv run pytest -q` が直接使える。ただし uv キャッシュ未生成の新ワークツリーでは `uv run --with pytest` が必要なことがある
- C: ドライブは逼迫気味（直近 ~16-48GB 変動）。ワーカーの TEMP データは `C:\Users\aruto\AppData\Local\Temp\opencode` に溜まるので、完了後は削除済みか確認する（8.6GB 残留した実績あり）
- `.gitignore` は `/competitions/*` を無視するが `!/competitions/competition1/` `!/competitions/competition2/` で中身を追跡。生成データは `competitions/competition1/organizer/data/` 等で個別無視
- 統合コミット時 pre-commit（ruff/ty）が走る。CRLF→LF 警告は無視してよい
- demo fixture の seed は市场構造変更のたびに `not_trained`（学習失敗）になることがある → prepare_example.py の seed を再設定（実績: 73 → 27）。コンペ規模（200/200）では密度が高くまず起きない
- `queenfish` ワークツリーには本プロジェクト外の作業が残っている。勝手に消さない
