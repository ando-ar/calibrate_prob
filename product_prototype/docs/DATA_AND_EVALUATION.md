# データと評価の定義

## 1. 目的変数は「紹介からH日以内の入社決定」

紹介日時を t、観測期限を as_of、観測期間を H 日とする。

```text
label = 1  if t <= kettei_dt < t + H and kettei_dt <= as_of
label = 0  otherwise, but only when t + H <= as_of
```

H日後ちょうどの決定は含めない。期限後の決定は「この期間内に決定しなかった」という0であり、「生涯決定しない」という意味ではない。日時は UTC に正規化し、業務日だけ設定タイムゾーンで作る。Hは24時間×日数の経過時間である。

初期値H=120は、紹介→応募のおおむね9割が7日以内、応募→書類通過のおおむね9割が14日以内、書類通過→決定のおおむね9割が約60日以内というユーザーの目安から、合計約81日に余裕39日を置く仮説。各段階の90%点を足しても全体の90%点とは限らない。実ログで紹介から決定までの分布を確認し、90/120/180日などを比較する場合は、その定義を凍結し評価期間を十分に確保する。

応募・通過も同じH日以内のイベントで段階を分類する。抽出の排他的な区分は、決定→通過のみ→応募のみ→未応募の優先順。応募7日以内／通過14日以内という別の打切りは適用しない。

## 2. 最新特徴の妥協とラベルの期間分割

特徴量は最新状態を使う。後に書き換わった職歴、選考中の状態、既存モデルの出力などから未来情報が入る可能性があり、時系列分割をしても取り除けない。全成果物で `latest_feature_leakage_accepted=true` と記録する。応募・通過・決定日時、実額、IDは直接の説明変数には使わない。

それとは別に、**学習時点でまだ確定していないラベル**が次期間から入り込むことは、既定の `purge_label_overlap=true` で避ける。

| 区分 | 紹介日時の範囲 |
| --- | --- |
| 学習 | train_start 以上、train_end−H 未満 |
| 検証 | train_end 以上、validation_end−H 未満 |
| 最終 | validation_end 以上、test_end 未満 |

従って、学習ラベルは検証開始時、検証ラベルは最終期間開始時までに観測可能になる。設定例では学習と検証の末尾120日を除く。`months` は**この実際の学習紹介期間の末尾**から遡る月数。生データの train_end を基準とする月数ではない。抽出 receipt に実際の紹介期間を出す。

全最終行が成熟するよう `test_end + H <= as_of` を必須にする。末尾の不確定行だけを都合よく負例扱いすることはしない。`purge_label_overlap=false` は過去の擬似分割との比較用だが、ラベルの期間重複を許す実験になる。

日ごとの紹介枠を評価するため、split 境界には業務日0時を使う。学習と検証に同じuser/itemが現れることは許容する。既存会員／既存求人への日次推薦が対象であり、新規主体への汎化テストではない。

## 3. 順位と紹介枠

1. 全候補へ同じモデルでスコアを計算する。
2. 同じ日・user・item の複数行は最高スコアの1行を採用する。同点は行IDの昇順。
3. 一人一日のスコア上位 `max_per_user_per_day` 行を残す。
4. 残った候補を日／任意の partition ごとに並べ、総枠を適用する。

総枠は既存コンペと同じ「その日その市場に現れる人数×5」が設定例。実プロダクトの枠に変更する。対象人数は**入力候補集合の distinct user**。別の名簿上の稼働人数は入力に含まれない。絶対数 `daily_budget` も指定でき、併用時は小さい方になる。総枠を省けば一人上限だけを適用する。

ユーザー上限は市場をまたいで一日合計にかかる。複数市場に同じ人がいる場合、手順3を市場別に行わない。これは単純な「個人上限→市場総枠」という二段階の割当であり、市場枠と個人枠の相互作用を含む最適マッチングではない。市場枠で落とした人の下位候補を他市場へ埋め戻す処理はない。

日付が変われば上限はリセットする。日をまたいだ再紹介抑制、求人別定員、担当者別工数、選考中ペアの除外はこの版のルールには加えていない。必要な業務適格条件は候補生成時点で適用する。

## 4. 指標が測っているもの

未紹介ペアはログにないので、評価用候補は**過去に紹介されたペアの集合**になる。非紹介ペアを0として追加しない。結果は固定された過去の紹介方策の下で観測したものなので、別の紹介集合を選んだときの競合・活動終了・企業の審査能力の変化は再現しない。

主な指標：

| 名前 | 定義 |
| --- | --- |
| macro_daily_observed_fee_yen | 選択行の決定実績×観測手数料の合計を日平均し、partitionを等重み平均 |
| macro_daily_observed_positive_proxy_yen | 上の金額を、全解法共通の給与代理額に置換 |
| observed_selected_positives | 選択した行の期間内決定件数（全期間合計） |
| observed_positive_capture | 観測した決定のうち選択行に残った割合 |
| average_precision / roc_auc | 分類器の決定予測値に対する指標。順位式の金額項は含まない |
| log_loss / brier | 抽出後の分類器出力を自然な検証分布へ適用した確率誤差 |
| observed_user/item_precision_at_k | 日別支援順位上位kの中で、ログ内に決定がある主体の割合を日平均 |

支援のuserスコアは上位5ペアの和、itemスコアは最大の1ペア。日内同一ペアを除いて、紹介上限や総枠をかける**前**に集約する。k=10,000、対象数が少なければ全件。支援が本当に必要か、介入で改善したかはこの正例からは分からない。過去コンペの「固定紹介方策で決定した主体」を、実ログで観測できる範囲に置き換えた診断指標である。

これらは反実仮想の推定売上ではない。`observed_*` と命名し、`evaluation_scope=logged_cohort_only_not_counterfactual_revenue` を記録する。実額を選出指標とする場合、検証・最終の全決定行で実額が必要。不明額を暗黙の0として勝敗を決めない。実額以外を指標に選んだ場合、実額不足件数を併記し、実額の合計は既知額だけの下限になる。

履歴の紹介数が新しい枠以下なら全行が選ばれ、順位方式に差が出ないことがある。`daily.csv` の candidates / selected を確認する。候補が足りないまま指標の同点を「解法が同等」と判断しない。

## 5. 出力スコアの読み方

重点抽出で正例を増やしたモデルの `probability` は、そのまま実母集団の決定確率を保証しない。`inverse_sampling` は今回の抽出確率の逆数を行損失に掛ける。これは過去の紹介方策による観測偏りを補正するものではなく、正しい実運用確率を保証するものでもない。

`p × fee` は期待額を狙う順位式、`p/(1-p) × fee` はオッズを使う別の順位式。金額が同じなら単調だが、金額が異なると順位は変わる。後者の p は計算時のみ [1e-9, 1−1e-9] に収める。どちらもこの版では未校正なので、スコアの円数を予算計画上の期待売上と解釈しない。
