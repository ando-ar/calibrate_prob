# market-density / evaluate / 20261118_112000

## 仮説

決定の希少さは求人レコメンドの難しさの本質であり、確率を引き上げずに市場密度を測れば、
観測実績リプレイ評価が統計的に使える（流入数・評価窓長・seed 数）の組み合わせを
数値で特定できる。

## 設定

- 対象: issue #39。読み取り専用の生成・集計のみ。src/ と test/ は未変更
  （再確認時 `uv run pytest -q` は 100 passed）。
- 生成 API: `MarketConfig` / `write_market_dataset`（synthetic-funnel 0.12.0、
  output_format=sqlite、`market_start=2025-01-01T00:00:00+09:00`、seed=71、
  referrals=5、application_days=20、posting_days=40）。
- config: 20/20×180d（warmup 90）を基準に、50/50×180d、100/100×180d、
  20/20×730d（warmup 365、proof 設定）を比較していた。
  **フォローアップで 150/150×180d と 200/200×180d（いずれも warmup 90、seed 71）を追加**。
  生成は一時ディレクトリで行い、DB / manifest / parquet はコミットしていない
  （200/200 は 336 万 events / 1.78 GiB で、days 短縮は不要だった）。
- 集計元: `daily`、`events`、`events_latent`、`user`、`item`。完全な数値表は
  `docs/MARKET_DENSITY.md`、圧縮版は `output/metrics.json`。

## 結果

- 新規流入は config 値で毎日一定（20/20、50/50、100/100、150/150、200/200）。在籍数は定常状態で
  求職者 ≈ 流入×20、求人 ≈ 流入×40 に収束（20/20 で 409 / 778、50/50 で 1,010 / 1,782、
  100/100 で 2,040 / 3,565、**150/150 で 3,068 / 5,348、200/200 で 4,090 / 7,130**）。
  日数を 730 に延ばしても定常値は不変。
- 紹介は 20/20 で約 838 件/日、50/50 で 3,856、100/100 で 8,881、
  **150/150 で 13,846、200/200 で 18,647**。当日に紹介が付かない在籍者の割合
  （warmup 後平均）は 34.1% / 13.6% / 9.9% / **8.5% / 8.2%**。
- 決定総数は 5 / 15 / 34 / **31 / 58** / 14 件（base / 50 / 100 / **150 / 200** / proof）。
  決定ゼロ日の割合は 97.2% / 91.7% / 82.8% / **85.6% / 73.3%** / 98.1%。
  150/150 の 31 件は 100/100 の 34 件より少ないが、30 件規模の小標本ノイズとして扱う
  （実現決定率 1.24×10⁻⁵ が低めの外れ値、200/200 は 1.73×10⁻⁵）。
- 実効 cap 使用率（5 件/日に到達した紹介ユーザー日の割合）は
  48.1% / 82.3% / 93.6% / **97.2% / 98.2%**（warmup 後 51.8% / 86.5% / 95.4% /
  **98.1% / 98.9%**）。150〜200/200 では cap が事実上完全に飽和している。
- 生プール（職種・地域・給与）は定常状態で平均 38.6 / 93.0 / 187.9 /
  **281.8 / 374.2** 件で空にならない。一方、既紹介ペアを除いた実効プールが 0 のユーザーは
  66.5% / 21.2% / 6.5% / **2.3% / 1.7%** で、枯渇はさらに小さくなった。
- 決定密度は紹介 1 件あたり実現 1.2〜2.1×10⁻⁵（`base` を除く）、潜在確率の積 1.1×10⁻⁴ で安定する。
  30 日窓 × 20 seed の期待観測決定数は 20/20 で 16.7、50/50 で 50.0、
  100/100 で 113.3、proof で 11.5、**150/150 で 103（warmup 後 120）、
  200/200 で 193（同 180）** 件。
- データ規模: 200/200 は 180 日 × 1 seed で **3,356,449 events / 1.777 GiB**
  （生成 180.4 秒、約 569 B/event）。20 seed では約 6,713 万 events / 約 35.6 GiB。

## 考察

主指標 `macro_daily_replay_fee_yen` が縮退するかは「評価窓内の観測決定数」で決まる。
20/20 の 30 日窓は 1 seed あたり期待 0.6〜1.0 件（P(決定 0) ≈ 44〜56%）で、
trial の 0 件は必然だった。20 seed でも期待 7〜12 件で集計値はノイズに対してまだ小さく、
単一シードの順位付けには使えない。50/50 は 30 日 × 20 seed で期待約 50 件となり、
集計主指標は非縮退で相対誤差も 14% 程度に収まる。100/100 は 5〜20 seed で
期待 28〜113 件で余裕がある。**150/150 は 1 seed で 5.2〜6.0 件（P(0) < 1%）、
20 seed で 103〜120 件。200/200 は 1 seed で 9.7 件（P(0) ≈ 0.01%）、20 seed で
180〜193 件**で、3〜5 seed あれば m ≳ 30 を満たす。

**cap とプールのどちらが律速か（追加チェック）**: 150/150 と 200/200 では cap 使用率が
97.2% / 98.2% に達し、1 人 5 件/日の枠はほぼ完全に実効化した。しかし日次紹介数自体は
8,881 → 13,846 → 18,647 とまだ増えており、1 流入あたり 88.8 → 92.3 → 93.2 件と
上限 100 に漸近しつつもフラット化はしていない。一方、実効プール 0 の割合は
6.5% → 2.3% → 1.7% に下がり、生プールも 188 → 282 → 374 件と増えた。
よって**プールは律速ではなく、実効的な上限は 5 件/日 cap と在籍者数（流入×20）の積**である。
単一シードの差を普遍的な優劣と結論づけていない。また確率の引き上げは提案しない
（希少さは仕様、要検討事項として分離）。

**データ規模のトレードオフ**: 200/200 の 30 日 × 20 seed は 1 seed あたり約 56 万 events で
合計約 1,119 万 events に相当し、決定数は十分すぎるほど得られる。しかし 180 日 × 20 seed で
約 35.6 GiB（50/50 の約 0.28 GiB/seed と比べ約 6.4 倍）、本番 1,825 日の 50/50 × 20 seed でも
約 57 GiB と見積もられ、記憶容量と生成時間が新しい制約になる。

## 結論（観測実績評価が使える組み合わせ）

- **50/50 流入 × 30 日評価窓 × 20 seed 以上**（期待決定 ≈ 50 件）が実用上の下限かつ本番既定。
- **100/100 流入 × 30 日窓 × 5〜20 seed**（期待 ≈ 28〜113 件）ならロバスト。
- **150/150 流入 × 30 日窓 × 1〜20 seed**（期待 ≈ 5〜120 件）で単一シードも非縮退。
- **200/200 流入 × 30 日窓 × 1〜20 seed**（期待 ≈ 9〜193 件）なら 3〜5 seed で安定。
  ただし 20 seed で約 36 GiB を要し、ストレージ余裕が条件。
- **20/20 流入は 30 日窓では不可**。評価窓を約 120〜180 日に延ばすか、
  30 日窓のまま seed を約 50 以上にする必要がある。
- 推奨は「決定数が十分なら 50/50 × 20 seed、少数 seed / 単一シードのロバスト性を優先し
  ディスク余裕があれば 100/100〜200/200」。流入を増やしても cap が律速のため
  1 流入あたり紹介数は 100 件/日 が天井であり、確率変更の提案は行わない。
